大模型的上下文 核心要点

理解 LLM 生成下一个 token 时"能看到"的全部内容——以及它的边界

一句话定义：大模型的上下文（Context）是模型在生成下一个 token 时能"看到"的所有内容——包括系统提示、对话历史、工具返回结果、检索到的文档。它被装在一个有大小限制的窗口（Context Window）里。它不是模型的"长期记忆"（关闭窗口就没了），也不是"数据库"（不能高效做条件查询）。

核心机制（6 个组件）

1. 上下文窗口 (Context Window)
有token 上限的滑动窗口（如 4K / 32K / 128K / 1M+ tokens）。超过上限的内容会被截断丢弃，模型再也"看不到"。
2. 注意力机制 (Attention)
Transformer 对窗口内所有 token 两两计算注意力，决定生成时"看"谁。复杂度 O(n²)，所以越长越慢越贵。
3. 上下文的组成
system prompt（角色与规则）+ 对话历史（user/assistant 消息）+ 工具结果（function call 返回）+ RAG 检索内容（从知识库拉来的相关文档）。
4. 位置编码 (Positional Encoding)
让模型知道token 之间的顺序（同一段话，顺序不同含义不同）。这是 Transformer 理解"上下文"的底层基础。
5. 上下文与成本的权衡
上下文越长，API 费用越高、延迟越大、显存占用越多。128K 上下文每次请求费用可能比 8K 高 15–30 倍。
6. "Lost in the Middle" 现象
研究显示，LLM 对开头和结尾的内容关注度高，对中间部分关注度低。所以"把关键信息塞中间"并不靠谱。

一个具体应用场景

场景：企业知识库问答系统（RAG + 上下文）
公司员工问："我们公司出差到北京的住宿报销标准是多少？"
  1. 系统先检索向量数据库，找到《差旅报销制度 v3.2》中相关段落
  2. 把系统提示 + 用户问题 + 检索到的相关段落 + 简短对话历史一起塞进 LLM 上下文
  3. LLM 基于这些上下文，精确引用报销标准（金额、城市、职位限制）
  4. 关键设计：只检索相关的 3–5 段，而不是把整本手册塞进去（避免噪声 + 节省 token）
  5. 如果用户追问"那机票呢？"，保留对话历史，让 LLM 知道上下文是"差旅"

容易混淆的问题与边界

坑 1：把上下文当记忆。关闭窗口内容就丢了。要长期记忆必须用外部存储（向量库、数据库、文件系统）+ 检索。
坑 2：以为上下文越长越好。研究显示超长上下文存在 "Lost in the Middle" 和性能衰减。128K ≠ 能用好 128K。
坑 3：忽视 token 成本。每次请求按输入+输出 token 计费，长上下文 = 高费用 + 高延迟。生产环境必须监控 token 用量。
边界：上下文适合"当前任务相关"的信息；不适合做"历史归档"（那个用向量库）或"精确查询"（那个用 SQL/数据库）。

自测题（5 道）

1. 大模型的"上下文"和"长期记忆"有什么区别？
看答案
上下文是当前请求时塞进窗口的全部内容，有大小限制、随请求结束就消失；长期记忆是跨请求持久化的外部存储（向量库、数据库、文件），需要通过检索等方式重新取回。
2. 上下文窗口越大越好吗？为什么？
看答案
不一定。窗口越大，① 成本和延迟显著增加 ② 模型对中间部分关注度可能下降（Lost in the Middle）③ 实际"有效利用"的长度和标称长度有差距。应按任务需求选择够用即可的窗口。
3. RAG（检索增强生成）和上下文是什么关系？
看答案
RAG 是给上下文"喂料"的手段：先用检索从知识库找到相关内容，再把内容塞进 LLM 上下文。RAG 解决的是"模型知识陈旧 / 不知道私有数据"的问题，靠的是上下文而非微调。
4. 上下文里通常装哪 4 类内容？
看答案
① system prompt（角色与规则）② 对话历史（user/assistant 消息）③ 工具返回结果（function call output）④ RAG 检索内容（从知识库拉来的相关文档）。
5. 为什么说"把关键信息塞中间"不靠谱？
看答案
因为 "Lost in the Middle" 研究显示 LLM 对超长上下文的开头和结尾关注度高，对中间部分关注度低。所以关键指令和重要信息应放在开头（系统提示）或结尾（最近消息）。
